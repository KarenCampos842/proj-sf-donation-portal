== Method ==
1. The owner of the project decided not to assign or change any permission set, so the checks were run with the permissions of the
   verifier user, as they are.
2. First choice, as instructed: read-only anonymous Apex (sf apex run) with SELECT statements only. It did NOT work, in three variants:
   static SOQL, dynamic SOQL (Database.query) and dynamic SOQL with WITH SYSTEM_MODE. All three stop with
   "No such column 'Status__c' on entity 'Payment_Attempt__c'": anonymous Apex applies the field visibility of the running user.
   No other route (a deployed helper class, a permission change) was tried.
3. Fallback: plain "sf data query" (SELECT only, --all-rows to include deleted records) on the fields the verifier user can read.
   Readable on Payment_Attempt__c: Id, Amount__c, Email__c, Visibility__c, Campaign__c, CreatedDate, IsDeleted.
   Readable on Donation__c: Id, Name, Amount__c, Payment_Status__c, Provider_Payment_Id__c, Confirmed_At__c, Attempt_Id__c, CreatedDate.
   NOT readable (no field permission): Payment_Attempt__c.Status__c, Preference_Id__c, Invoice_Requested__c, Public_Name__c,
   Privacy_Notice_Accepted__c, Privacy_Notice_Accepted_At__c, Donor_Confirmed_At__c, Superseded_At__c, Portal_Access_Token_Hash__c, and
   Donation__c.Privacy_Notice_Accepted__c / Privacy_Notice_Accepted_At__c. The value of the hash was never read or printed.
4. Precision: the Salesforce CLI turns numbers into JavaScript floating point before printing them, so a 16-digit amount shows one cent
   less (99999999999999.98). The amounts below were read as text with FORMAT(Amount__c) and confirmed with exact filters
   (Amount__c = 99999999999999.99 returns 1 record; Amount__c = 99999999999999.98 returns 0).
